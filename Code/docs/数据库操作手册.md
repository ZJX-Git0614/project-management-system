# Ceastar PMS 数据库操作手册

> 文档版本：1.3  
> 最后更新：2026-08-04  
> 适用范围：本机开发、Windows Docker、飞牛 OS Docker 生产环境  
> 数据库：PostgreSQL 16 + Prisma ORM

## 1. 使用范围

本手册供系统管理员、开发人员和数据库维护人员使用，覆盖：

- PostgreSQL 连接与状态检查；
- 常见数据查询、增加、修改和删除；
- 数据备份、校验和灾难恢复；
- Navicat、Prisma Studio 和 `psql` 的安全连接方式；
- 数据库结构迁移和版本兼容规范；
- 蓝绿部署期间的数据库操作边界；
- 故障排查和高风险命令限制。

日常业务数据应优先通过 Ceastar PMS 页面或 API 操作。直接执行 SQL 会绕过权限校验、业务编号重排、字段联动和操作日志，只适合查询、诊断、数据修复和经审核的批量维护。

## 2. 数据安全基本原则

1. 修改前先确认当前连接的主机、数据库和用户。
2. 生产环境写操作前必须生成并验证数据库备份。
3. 写操作必须先在事务中执行，核对影响行后再提交。
4. 查询和更新必须使用稳定主键 `id`，不能用任务名称、事项名称等可变字段作为关联条件。
5. 不直接修改密码哈希、迁移台账或加密密钥。
6. 不在生产环境执行 `prisma db push`。
7. 不执行 `docker compose down -v`，它会删除数据库和文档存储卷。
8. 应用回滚和数据库恢复是两件事：普通版本回退只切回旧应用，不恢复旧数据库。

## 3. 当前数据库配置

| 环境 | PostgreSQL 服务 | 数据库 | 用户 | 默认容器名 |
| --- | --- | --- | --- | --- |
| Windows Docker | `postgres` | `pms` | `pms` | `pms-postgres` |
| 飞牛 OS Docker | `postgres` | `pms` | `pms` | Compose 自动生成或 `pms-postgres` |
| 本机开发 | 本机 PostgreSQL | `project_mgmt` | 当前本机用户 | 无 |

生产密码位于部署目录的 `.env`：

```dotenv
POSTGRES_PASSWORD=实际数据库密码
```

不要将 `.env` 内容发到聊天、截图、日志或代码仓库。

PostgreSQL 容器内端口固定为 `5432`。宿主机端口可以映射为其他端口，例如 `15432:5432` 表示宿主机使用 `15432`，容器内部仍使用 `5432`。

## 4. 连接数据库

### 4.1 Windows Docker

在包含 `docker-compose.yml` 的部署目录打开 PowerShell：

```powershell
docker compose ps
docker compose exec postgres psql -U pms -d pms
```

如果当前目录不方便，也可以按容器名进入：

```powershell
docker exec -it pms-postgres psql -U pms -d pms
```

### 4.2 飞牛 OS Docker

通过 SSH 登录飞牛 OS，进入部署目录：

```bash
cd /vol1/实际目录/Ceastar-PMS
docker compose ps
sudo docker compose exec postgres psql -U pms -d pms
```

### 4.3 本机开发数据库

```bash
psql "postgresql://zhaojiaxin@localhost:5432/project_mgmt"
```

也可以在 `Code` 目录启动 Prisma Studio：

```bash
npx prisma studio
```

Prisma Studio 适合查看和少量修改数据，但同样会绕过系统业务接口。

## 5. psql 常用命令

以下命令在进入 `psql` 后执行：

```sql
\conninfo                    -- 当前连接信息
\l                           -- 数据库列表
\dn                          -- Schema 列表
\dt                          -- public Schema 下的表
\d "Project"                -- 查看项目表结构
\d+ "ProjectGanttTask"       -- 查看甘特任务详细结构
\di                          -- 索引列表
\x auto                      -- 宽记录自动纵向显示
\timing on                   -- 显示 SQL 执行时间
\pset pager off              -- 关闭分页器
\q                           -- 退出
```

Prisma 创建的表和字段使用大小写名称，SQL 中必须使用双引号，例如 `"ProjectGanttTask"` 和 `"projectId"`。

## 6. 核心业务表

| 表 | 用途 | 主要关联键 |
| --- | --- | --- |

## 7. 常用查询

### 7.1 确认数据库和版本

```sql
SELECT current_database(), current_user, version();
SELECT NOW() AS "数据库时间";
```

### 7.2 查询项目

```sql
SELECT "id", "name", "code", "status", "createdAt", "updatedAt"
FROM "Project"
ORDER BY "createdAt";
```

### 7.3 查询甘特任务

```sql
SELECT "id", "taskCode", "taskName", "taskCategory",
       "durationDays", "startDate", "finishDate", "progress", "sortOrder"
FROM "ProjectGanttTask"
WHERE "projectId" = '项目ID'
ORDER BY "sortOrder";
```

### 7.4 查询任务依赖

```sql
SELECT predecessor."taskCode" AS "紧前任务",
       successor."taskCode" AS "后续任务",
       dependency."type", dependency."lag"
FROM "ProjectGanttDependency" dependency
JOIN "ProjectGanttTask" predecessor
  ON predecessor."id" = dependency."predecessorTaskId"
JOIN "ProjectGanttTask" successor
  ON successor."id" = dependency."successorTaskId"
WHERE dependency."projectId" = '项目ID'
ORDER BY successor."sortOrder";
```

### 7.5 查询事项与关联任务

```sql
SELECT matter."matterCode", matter."title", matter."status",
       task."taskCode", task."taskName"
FROM "WeeklyItem" matter
LEFT JOIN "WeeklyItemGanttTask" matter_task
  ON matter_task."weeklyItemId" = matter."id"
LEFT JOIN "ProjectGanttTask" task
  ON task."id" = matter_task."ganttTaskId"
WHERE matter."projectId" = '项目ID'
ORDER BY matter."sortOrder", task."sortOrder";
```

### 7.6 查询风险与关联事项

```sql
SELECT risk."riskCode", risk."riskName", risk."level", risk."status",
       matter."matterCode", matter."title"
FROM "RiskRegisterItem" risk
LEFT JOIN "RiskRegisterItemWeeklyItem" risk_matter
  ON risk_matter."riskItemId" = risk."id"
LEFT JOIN "WeeklyItem" matter
  ON matter."id" = risk_matter."weeklyItemId"
WHERE risk."projectId" = '项目ID'
ORDER BY risk."sortOrder", matter."sortOrder";
```

风险只能关联事项。风险的受影响 WBS 任务来自所有关联事项的任务并集：

```sql
SELECT DISTINCT risk."riskCode", risk."riskName",
       task."taskCode", task."taskName", task."sortOrder"
FROM "RiskRegisterItem" risk
INNER JOIN "RiskRegisterItemWeeklyItem" risk_matter
  ON risk_matter."riskItemId" = risk."id"
INNER JOIN "WeeklyItemGanttTask" matter_task
  ON matter_task."weeklyItemId" = risk_matter."weeklyItemId"
INNER JOIN "ProjectGanttTask" task
  ON task."id" = matter_task."ganttTaskId"
WHERE risk."projectId" = '项目ID'
ORDER BY risk."riskCode", task."sortOrder";
```

### 7.7 数据量统计

```sql
SELECT 'Project' AS "表", COUNT(*) AS "数量" FROM "Project"
UNION ALL SELECT 'ProjectGanttTask', COUNT(*) FROM "ProjectGanttTask"
UNION ALL SELECT 'WeeklyItem', COUNT(*) FROM "WeeklyItem"
UNION ALL SELECT 'RiskRegisterItem', COUNT(*) FROM "RiskRegisterItem"
UNION ALL SELECT 'ProjectDocumentFile', COUNT(*) FROM "ProjectDocumentFile";
```

## 8. 安全增删改查

### 8.1 标准事务模板

```sql
BEGIN;

-- 执行 INSERT、UPDATE 或 DELETE

-- 检查实际结果和影响范围
SELECT ...;

-- 结果正确时执行
COMMIT;

-- 结果不正确时不要 COMMIT，改为执行
-- ROLLBACK;
```

### 8.2 修改一条风险

```sql
BEGIN;

UPDATE "RiskRegisterItem"
SET "status" = '已关闭',
    "updatedAt" = NOW()
WHERE "id" = '风险ID'
RETURNING "id", "riskCode", "riskName", "status";

COMMIT;
```

直接执行 SQL 时，必须同步更新带有 `updatedAt` 的记录；Prisma 的 `@updatedAt` 只在通过 Prisma Client 更新时自动生效。

### 8.3 新增风险示例

```sql
BEGIN;

INSERT INTO "RiskRegisterItem"
  ("id", "createdAt", "updatedAt", "projectId", "riskName")
VALUES
  ('manual_' || md5(random()::text || clock_timestamp()::text),
   NOW(), NOW(), '项目ID', '新增风险名称')
RETURNING "id", "riskName";

COMMIT;
```

系统业务 ID、排序和日志可能需要额外重排，因此项目、甘特任务和事项不建议直接 `INSERT`，应通过页面或 API 新增。

### 8.4 删除单条风险

```sql
BEGIN;

SELECT "id", "riskCode", "riskName"
FROM "RiskRegisterItem"
WHERE "id" = '风险ID';

DELETE FROM "RiskRegisterItem"
WHERE "id" = '风险ID'
RETURNING "id", "riskCode", "riskName";

COMMIT;
```

删除 `Project` 或父级 `ProjectGanttTask` 会触发级联删除，禁止在未核对关联数量和备份的情况下直接操作。

### 8.5 查询即将被级联删除的数据

```sql
SELECT
  (SELECT COUNT(*) FROM "ProjectGanttTask" WHERE "projectId" = '项目ID') AS "任务",
  (SELECT COUNT(*) FROM "WeeklyItem" WHERE "projectId" = '项目ID') AS "事项",
  (SELECT COUNT(*) FROM "RiskRegisterItem" WHERE "projectId" = '项目ID') AS "风险",
  (SELECT COUNT(*) FROM "ProjectBudgetItem" WHERE "projectId" = '项目ID') AS "预算明细";
```

## 9. 备份

### 9.1 推荐方式

在系统中进入：

```text
系统设置 -> 系统数据管理 -> 数据备份与恢复
```

手动备份会同时保存 PostgreSQL 数据库、项目文档、备份记录和校验信息。生产环境优先使用该入口。

### 9.2 Docker 命令行备份

在部署目录执行：

```bash
docker compose exec -T postgres sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom --no-owner --no-privileges -f /tmp/database.dump'

docker compose cp postgres:/tmp/database.dump ./backups/database.dump
docker compose exec -T postgres rm -f /tmp/database.dump
```

不要使用 Windows PowerShell 5 的二进制重定向直接生成 `.dump`，避免输出流编码损坏。使用 `docker compose cp` 复制二进制备份。

### 9.3 校验备份

```bash
docker compose cp ./backups/database.dump postgres:/tmp/database-check.dump
docker compose exec -T postgres pg_restore --list /tmp/database-check.dump
docker compose exec -T postgres rm -f /tmp/database-check.dump
```

校验清单至少应包含 `Project`、`UserAccount` 和 `ProjectGanttTask` 的表与数据项。仅有备份文件但没有校验和恢复演练，不视为有效备份。

## 10. 数据库恢复

数据库恢复会替换当前数据库内容，并可能丢失备份时间点之后的所有数据。恢复前必须停止用户写入，并再次生成现场保护备份。

### 10.1 推荐方式

优先使用“系统数据管理”的数据库导入功能。系统会执行备份格式校验、清理目标 Schema、恢复数据并补齐当前版本的增量迁移。

### 10.2 飞牛 OS 部署脚本

```bash
cd /vol1/实际目录/Ceastar-PMS
sudo ./restore.sh backups/manual-YYYYMMDD-HHMMSS RESTORE
```

脚本会先创建保护备份，停止 PMS，重新创建 `pms` 数据库，恢复数据库和项目文档，再启动服务。

### 10.3 手动数据库恢复

仅在系统恢复入口和部署脚本都不可用时执行：

```bash
docker compose stop pms

# 先执行第 9 章的现场保护备份
docker compose cp ./backups/database.dump postgres:/tmp/database.dump

docker compose exec -T postgres dropdb -U pms --if-exists --force pms
docker compose exec -T postgres createdb -U pms -O pms pms
docker compose exec -T postgres pg_restore \
  -U pms -d pms --exit-on-error --no-owner --no-privileges /tmp/database.dump

docker compose exec -T postgres rm -f /tmp/database.dump
docker compose up -d pms
docker compose ps
```

恢复后必须检查登录、项目数量、任务数量、事项、风险、预算和文档，并执行当前版本要求的增量迁移。不要使用 `pg_restore --clean` 直接覆盖运行中的数据库，它可能因新版本外键依赖而无法删除旧主键。

## 11. Navicat 安全连接

当前正式部署默认不向局域网暴露 PostgreSQL。需要 Navicat 时，在 `postgres` 服务下临时增加仅本机监听：

```yaml
ports:
  - "127.0.0.1:15432:5432"
```

应用配置：

```bash
docker compose up -d postgres
```

Navicat 连接参数：

| 参数 | 值 |
| --- | --- |
| 主机 | `127.0.0.1` |
| 端口 | `15432` |
| 数据库 | `pms` |
| 用户名 | `pms` |
| 密码 | 部署目录 `.env` 中的 `POSTGRES_PASSWORD` |

连接飞牛 OS 时推荐使用 SSH 隧道，不要直接把 PostgreSQL 暴露到整个局域网：

```bash
ssh -L 15432:127.0.0.1:15432 ZJX@飞牛OS地址
```

SSH 会话保持运行，Navicat 继续连接 `127.0.0.1:15432`。

## 12. 常见诊断命令

```bash
docker compose ps
docker compose logs --tail=200 postgres
docker compose logs --tail=200 pms
docker compose exec postgres pg_isready -U pms -d pms
docker compose exec postgres psql -U pms -d pms -c 'SELECT NOW();'
docker stats --no-stream
docker system df
```

查看数据库大小：

```sql
SELECT pg_size_pretty(pg_database_size(current_database())) AS "数据库大小";

SELECT relname AS "表",
       pg_size_pretty(pg_total_relation_size(relid)) AS "占用空间"
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

查看当前连接和长事务：

```sql
SELECT pid, usename, application_name, state,
       xact_start, query_start, LEFT(query, 160) AS query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

查看外键：

```sql
SELECT conrelid::regclass AS "子表",
       confrelid::regclass AS "父表",
       conname AS "约束"
FROM pg_constraint
WHERE contype = 'f'
ORDER BY 1, 2;
```

## 13. 禁止或高风险操作

以下操作未经完整备份和维护窗口不得执行：

```sql
DROP DATABASE pms;
DROP SCHEMA public CASCADE;
TRUNCATE TABLE ... CASCADE;
DELETE FROM "Project";
ALTER TABLE ... DROP COLUMN ...;
UPDATE "UserAccount" SET "passwordHash" = ...;
DELETE FROM "_prisma_migrations";
```

同样禁止：

```bash
docker compose down -v
docker volume rm ceastar-pms_pgdata
npx prisma db push --accept-data-loss
```

## 14. 数据库结构更新规范

### 14.1 开发流程

1. 修改 `prisma/schema.prisma`。
2. 在 `prisma/manual-migrations/` 新增按日期命名的 SQL 文件。
3. SQL 必须可重复执行或在执行前检查对象是否存在。
4. 先在备份恢复出来的测试数据库验证。
5. 执行 Prisma Client 生成、类型检查、测试和生产构建。
6. 更新本手册的核心表、字段说明、迁移流程和变更记录。
7. 更新部署包并验证旧版本数据库可以升级。

验证命令：

```bash
npx prisma generate
npm run typecheck
npm run lint
npm test -- --run
npm run build
```

### 14.2 蓝绿部署迁移原则

数据库使用 `Expand -> Migrate -> Contract`：

1. **Expand**：先增加新表、可空字段、安全默认值或新索引，旧应用仍可运行。
2. **Migrate**：分批回填数据，应用在过渡期同时兼容新旧字段。
3. **Contract**：至少延迟一个正式版本，在旧应用回滚窗口结束后再删除旧字段。

普通蓝绿回滚只切回旧应用，不恢复旧数据库。只有数据损坏时才停止写入并执行灾难恢复。

禁止在同一个发布包中同时新增替代字段、切换应用并删除旧字段。索引和大表回填应避免长时间锁表。

### 14.3 手册同步要求

以下任一内容变化时，本文件必须在同一提交中同步更新：

- `prisma/schema.prisma` 中新增、删除或修改模型与字段；
- `prisma/manual-migrations/` 中新增结构或数据迁移；
- PostgreSQL、Prisma 或部署架构版本变化；
- 数据库容器名、数据库名、端口或连接方式变化；
- 备份、恢复、加密、权限和蓝绿部署流程变化；
- 新增需要管理员直接维护的业务表。

代码评审和发布检查必须包含“数据库操作手册是否同步”一项。数据库变化但本手册未更新时，不应构建正式更新包。

### 14.4 角色关联完整性修复

`20260804_role_reference_integrity.sql` 是可重复执行的数据修复迁移，用于清理旧版本删除角色后留下的关联数据：

- 从 `UserAccount.assignedRoleNames` 中移除 `RoleConfig` 中已不存在的角色；
- 删除引用已不存在角色的 `ProjectMember` 记录，由外键将关联 WBS 任务的 `ownerMemberId` 置空；
- 清空通过新旧事项/风险关联链路受该 WBS 任务影响的负责人文本，避免继续显示旧负责人；
- 按启用账号重建 `RoleConfig.persons` 快照，并从 `PermissionTree` 中移除已删除角色的权限键。

如果 `assignedRoleNames` 或 `PermissionTree.data` 已损坏为非法 JSON，迁移会保留原值并跳过该记录，避免以空数组或空对象覆盖现场数据；管理员应在备份后单独修复损坏记录。

该迁移会在容器启动时自动执行。绿色候选环境启动前已由更新脚本生成数据库备份，因此不应跳过更新前备份步骤。

### 14.5 事项与风险多关联迁移

`20260804_multi_relation_links.sql` 新增 `WeeklyItemGanttTask` 和 `RiskRegisterItemWeeklyItem` 两张关联表，并将旧字段中的单一关联自动回填到新表。新版本中，项目事项可关联多个 WBS 任务，风险可关联多个项目事项；风险受影响任务由所关联事项的 WBS 任务并集自动推导。旧的 `ganttTaskId` 和 `weeklyItemId` 在蓝绿回滚窗口内保留，并同步记录首个关联。

### 14.6 执行阶段与 WBS 关联迁移

`20260823_project_execution.sql` 新增 `ProjectExecution` 和 `ProjectExecutionTask`。
执行阶段只保存名称、类型、状态、负责人和说明，所有计划范围、进度和任务明细都从 `ProjectGanttTask` 实时汇总；删除 WBS 任务时，关联记录由外键级联删除，避免出现悬空执行阶段任务。

该迁移不插入任何默认业务数据，可重复执行。更新应用前先生成数据库保护备份，再执行 `npx prisma generate` 和结构迁移；回滚应用版本时保留这两张表，不需要回滚数据库。

### 14.7 项目交付与采购管理迁移

`20260906_project_delivery_procurement.sql` 新增交付物、交付状态、物料清单版本、物料行、采购条目和采购状态日志。迁移采用可重复执行的建表、索引和外键保护逻辑，不插入演示或默认业务数据。

本次结构约束包括：

- 同一交付物、阶段和清单类型的版本号唯一；数据库仅允许一个 `RELEASED` 当前版本；
- 同一项目与源物料行仅允许一个采购条目，防止并发同步重复创建；
- 已关联物料版本的项目文档使用限制删除外键，不能先删除原始清单破坏审计链；
- 项目、交付物、物料版本和采购条目建立查询索引，采购经办人、预算和 WBS 关联使用可空外键。

生产升级顺序：先生成并校验数据库与项目文档保护备份，再执行迁移、`npx prisma generate`、类型检查和应用构建，最后验证交付物查询、物料版本发布、BOM 同步预览、采购状态变更及项目恢复。若唯一索引因历史重复数据创建失败，应停止发布并人工核对重复记录，不得删除任意一条后强行继续。

旧应用不读取新增表，因此应用版本可以直接回退并保留新增数据；数据库结构不做在线反向删除。只有确认迁移造成数据损坏时，才按第 10 节从升级前保护备份恢复数据库与项目文档。

## 15. 故障处理顺序

1. 停止继续执行未知 SQL，不立即重启或删除容器。
2. 保存报错原文、时间、当前版本和操作步骤。
3. 执行 `docker compose ps` 和日志检查。
4. 在不覆盖现场的前提下创建保护备份。
5. 确认是应用问题、迁移问题、数据问题还是存储问题。
6. 应用问题优先切回旧版本；不要同时恢复数据库。
7. 只有确认数据损坏时才进入数据库恢复流程。
8. 恢复后核对核心表数量、关联键、登录和项目文档。
