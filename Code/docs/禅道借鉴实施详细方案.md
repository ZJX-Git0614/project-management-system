# 禅道借鉴实施详细方案

## 1. 方案定位

本方案基于《禅道与PMS差异及借鉴建议.md》，把“可以借鉴”转化为可落地的产品、数据、权限、流程和测试方案。

方案目标不是把 PMS 改造成禅道，也不是复制禅道的菜单，而是保留 PMS 的正式项目计划能力，补齐研发过程管理能力：

```text
项目/产品上下文
        -> 需求与交付目标
        -> PMS WBS 正式计划
        -> 执行阶段与协同工作
        -> 缺陷/测试/验收
        -> 基线、进度审批、挣值和项目复盘
```

核心原则：

1. **WBS 是唯一计划事实来源**：阶段、看板、助手和报表都引用 WBS，不复制计划日期。
2. **业务关联使用不可变数据库 ID**：名称、任务 ID、显示编号都不能承担外键职责。
3. **计划、执行、实际投入分离**：计划日期、执行状态、实际工时和进度审批不能混成一个字段。
4. **所有跨模块动作可追溯**：导入、导出、排期、基线、审批、恢复、助手操作均留下操作记录。
5. **新模块可关闭**：没有启用需求/测试管理的项目，不显示空模块，不人为产生数据。
6. **助手先理解再行动**：先识别对象、范围、过滤条件和目标，再查询或写入；写入必须经过权限和审批。

## 2. 目标业务架构

### 2.1 对象层级

建议形成以下对象关系：

```text
项目集/客户群（可选）
  ├─ 产品/设备型号（可选）
  │    ├─ 需求/交付目标
  │    └─ 版本/里程碑
  └─ 项目
       ├─ 执行阶段/工作包
       ├─ WBS任务（唯一正式计划）
       ├─ 项目事项
       ├─ 风险
       ├─ 文档
       ├─ 缺陷
       ├─ 测试用例/测试执行
       ├─ 审批实例
       └─ 实际工时/活动记录
```

其中：

- 项目集和产品是跨项目管理对象，初期可以关闭。
- 执行阶段是禅道“执行/迭代”的借鉴对象，负责组织任务和协同，不拥有独立计划日期。
- WBS 任务仍然负责任务层级、负责人、依赖、工期、日期、资源和关键路径。
- 需求、事项、风险、缺陷、测试用例和文档通过关联表连接，不互相改写名称。

### 2.2 计划事实唯一性

一个任务只能有一份正式计划：

- `ProjectGanttTask.planStartDate/planEndDate` 是正式计划日期。
- T0 正排、完成日期倒排、工作日历、FS 依赖、资源冲突和关键路径都由同一排期引擎计算。
- 执行阶段只能显示所包含任务的汇总日期：最早开始 = 任务最早开始，最晚完成 = 任务最晚完成。
- 看板拖动状态不会修改日期；拖动日期必须进入排期预览和影响确认。
- 需求、缺陷和测试只引用任务，不直接保存另一份任务计划日期。

## 3. 第一优先级：执行阶段/工作包

### 3.1 业务目的

借鉴禅道执行模块，把一个复杂项目拆成可管理的阶段，例如：

- 需求分析
- 方案设计
- 采购
- 样机生产
- 测试验证
- 量产
- 交付验收

阶段解决“当前应该看哪一组任务”的问题，WBS 解决“这些任务具体如何排期”的问题。

### 3.2 功能范围

每个阶段包含：

- 阶段名称、阶段类型、阶段负责人
- 计划范围：引用 WBS 任务或 WBS 节点
- 阶段状态：未开始、进行中、已挂起、已完成、已关闭
- 阶段目标、说明、里程碑
- 阶段看板和列表
- 阶段风险、事项、文档和审批入口

### 3.3 数据建议

建议新增 `ProjectExecution`：

| 字段 | 说明 |
|---|---|
| `id` | 不可变主键 |
| `projectId` | 所属项目 |
| `name` | 阶段名称 |
| `type` | 短期、长期、运维或自定义类型 |
| `ownerId` | 阶段负责人 |
| `status` | 阶段状态 |
| `description` | 阶段说明 |
| `sortOrder` | 阶段排序 |
| `createdAt/updatedAt` | 审计时间 |

建议新增 `ProjectExecutionTask`：

- `executionId`
- `ganttTaskId`
- `relationType`：直接引用、包含子树、动态筛选
- `createdAt`

不在 `ProjectExecution` 中保存 `planStartDate`、`planEndDate`、`duration`。如果页面需要显示阶段日期，实时从 WBS 汇总。

### 3.4 阶段与任务的边界

- 阶段可以批量查看任务，但不能绕过 WBS 修改任务日期。
- 阶段状态由任务完成比例、审批结果和人工状态共同决定，显示计算依据。
- 阶段负责人可以管理协同内容，但不自动获得项目 WBS 修改权限。
- 删除阶段只删除引用关系，不删除 WBS 任务。
- 删除任务时，必须先处理阶段引用：阻断、转移或保留失效引用，不能静默删除。

### 3.5 验收标准

1. 创建阶段并关联 WBS 后，阶段列表能显示任务数、完成比例和计划范围。
2. WBS 日期变化后，阶段日期自动更新，不产生第二套日期。
3. 阶段看板移动任务状态不会改动 WBS 计划日期。
4. 删除 WBS 任务时，系统明确提示受影响的阶段、需求、缺陷、测试和文档关联。

## 4. 第二优先级：需求、缺陷和测试闭环

### 4.1 对象定义

#### 需求/交付目标

表达客户、产品或项目需要交付的内容，包含：

- 需求 ID、标题、描述、来源、优先级、状态
- 所属产品/项目
- 验收标准
- 目标版本或里程碑
- 关联 WBS 任务和文档

#### 缺陷

表达已经验证或使用中发现的问题，包含：

- 缺陷 ID、标题、描述、严重程度、优先级
- 发现人、负责人、发现版本、修复版本
- 状态：待确认、已确认、处理中、待验证、已关闭、拒绝
- 重现步骤、期望结果、实际结果、附件
- 关联需求、WBS 任务、测试用例和测试执行

#### 测试用例

表达可重复的验证步骤，包含：

- 用例 ID、标题、前置条件、步骤、预期结果
- 优先级、类型、适用版本
- 关联需求和 WBS 任务

#### 测试执行

表达一次具体测试活动，包含：

- 测试执行名称、范围、负责人、计划日期
- 关联测试用例
- 每个用例的通过、失败、阻塞、未执行结果
- 关联缺陷和测试报告

### 4.2 建议关联模型

```text
Requirement 1 -- N ProjectGanttTask
Requirement 1 -- N TestCase
ProjectGanttTask 1 -- N Defect
TestCase 1 -- N Defect
TestRun N -- N TestCase
Defect N -- N ProjectGanttTask
```

所有关系使用独立关联表：

- `RequirementGanttTask`
- `RequirementTestCase`
- `DefectGanttTask`
- `DefectTestCase`
- `TestRunCase`
- `TestRunDefect`

### 4.3 与风险登记册的区别

- 风险是尚未确定是否发生的不确定性，强调概率、影响、应对和责任人。
- 缺陷是已经观察到的偏差或错误，强调重现、修复和验证。
- 事项是需要推进或跟踪的工作，不等同于风险或缺陷。

三者可以互相关联，但不应合并成一张表：

```text
风险 -> 预防/应对事项
缺陷 -> 修复任务
事项 -> 执行跟踪
```

### 4.4 质量门禁

建议在发布基线、提交验收和关闭阶段前增加可配置门禁：

- 关键缺陷未关闭时禁止发布。
- 关联需求没有验收标准时提示不完整。
- 关键测试用例未执行时提示风险。
- 测试失败但没有缺陷记录时提示补充。
- 门禁可以配置为阻断、强提醒或仅记录。

## 5. 第三优先级：工时和资源闭环

### 5.1 四类时间必须分开

| 类型 | 含义 | 来源 |
|---|---|---|
| 计划工期/预计工时 | 完成计划需要多少时间 | 排期引擎和任务输入 |
| 已用工时 | 已经投入多少人时 | 工作日志/进度提交 |
| 剩余工时 | 还需要投入多少人时 | 负责人更新或审批后计算 |
| 实际日期 | 实际开始和实际完成日期 | 负责人提交并按规则审批 |

不能使用“当前进度百分比”直接代替已用工时，也不能用计划工期直接当成本。

### 5.2 工作日志

建议新增 `TaskWorkLog`：

- `taskId`
- `userId`
- `workDate`
- `hours`
- `description`
- `status`：草稿、已提交、已批准、已驳回
- `approvedBy/approvedAt`
- `createdAt/updatedAt`

规则：

- 末级任务负责人只能提交自己负责任务的工时。
- 父级任务不直接录入实际工时，父级工时由子任务汇总。
- 每人每天工时不能超过系统配置上限，超出需要审批或明确标记加班。
- 工作日志审批不修改基线，只影响实际投入和挣值数据。

### 5.3 资源视图

借鉴禅道每天每人最大工时的配置思路，增加：

- 人员日历
- 法定节假日
- 请假/不可用时段
- 每日标准工时 7.5 小时
- 加班工时
- 按负责人、角色、阶段、日期查看负载

资源冲突展示必须区分：

- 计划冲突：同一人员在同一工作时间被多个任务占用。
- 实际超时：已用工时超过可用容量。
- 计划外加班：任务仍在父级边界内，但需要额外工作时长。
- 硬边界冲突：无论如何排期都无法满足父级或项目完成边界。

## 6. 第四优先级：看板、动态和保存视图

### 6.1 统一视图模型

所有核心模块复用同一种视图配置：

- `moduleKey`
- `projectId`
- `filterJson`
- `visibleColumns`
- `sortJson`
- `groupBy`
- `viewType`
- `ownerId`
- `isShared`

视图类型：

1. 列表：批量处理。
2. 看板：按状态、阶段、负责人或风险等级分组。
3. 时间线：只显示有计划日期的对象。
4. 统计：聚合数量、工时、成本、状态和趋势。

### 6.2 动态流

建议建立统一 `ActivityEvent`，记录：

- 对象类型和对象 ID
- 操作类型
- 操作人
- 变更前后摘要
- 关联审批实例
- 关联通知
- 时间和来源（页面、导入、助手、API）

动态流不能只保存一段文本，必须保留结构化变更，才能支持审计、助手查询和回滚说明。

### 6.3 看板约束

- 看板拖动只修改状态或排序，不直接改变 WBS 计划。
- 改变负责人、日期、工期、依赖必须进入对应业务流程。
- 看板卡片显示对象 ID，避免同名对象无法区分。
- 看板必须支持权限过滤，用户不能看到没有权限的任务或缺陷。

## 7. 第五优先级：文档空间和版本

### 7.1 空间划分

借鉴禅道的空间结构，PMS 文档可以增加逻辑空间：

- 项目交付空间
- 研发设计空间
- 测试验证空间
- 团队模板空间
- 接口和技术资料空间

物理文件仍由当前文档目录、本地备份目录或公司云盘配置保存。

### 7.2 文档关联

文档可以关联：

- 项目
- 执行阶段
- WBS 任务
- 需求
- 缺陷
- 测试用例
- 审批实例

删除任务或对象时不删除原文件，除非管理员明确执行物理文件清理；关联失效必须显示提示并进入待处理列表。

### 7.3 版本和审计

- 同一文档保留版本号、上传人、上传时间和变更说明。
- 下载、替换、删除和恢复都记录操作日志。
- 云盘上传失败时保留本地文件和待同步状态，不能显示为已完成。
- 文档内容和元数据备份必须分开验证。

## 8. 权限和审批设计

### 8.1 权限分层

建议使用四层权限：

1. 系统权限：模块开关、账号、角色、备份、流程定义。
2. 项目权限：项目查看、WBS 编辑、项目成员、预算、风险和文档。
3. 对象权限：任务负责人、需求负责人、缺陷负责人、测试负责人。
4. 操作权限：导入、导出、自动排期、发布基线、恢复数据、助手写入。

### 8.2 借鉴 Agent 的三档授权

佳佳继续保留三档操作授权：

- 请求批准：每次写操作单独确认。
- 代为审批：允许执行已授权的审批动作，但不能越过权限范围。
- 完全访问：仅限明确授权的系统管理员，仍保留审计和高风险操作拦截。

### 8.3 审批边界

- 计划日期、工期、依赖、负责人变化：可能影响正式排期，需要排期影响确认。
- 基线发布/变更：走基线审批，项目经理或授权角色执行。
- 进度、实际工时、实际完成日期：走进度审批，不变更基线。
- 缺陷关闭、测试通过、阶段关闭：可配置质量审批。
- 数据恢复、批量删除：仅超级管理员，并要求二次确认和备份记录。

## 9. 佳佳 Agent 适配方案

### 9.1 动态模块发现

不能继续只依赖固定提示词。建议建立 `AssistantModuleRegistry`，注册：

- 模块名称和显示名称
- 对象类型
- 可查询字段
- 可导出字段和模板
- 可执行工具
- 权限要求
- 关联对象
- 删除/置空/审批约束
- 示例问题

新增模块时只需注册模块和工具，助手即可检索到它。

### 9.2 意图解析流程

用户说“导出前端一级任务并总结进度”时，助手必须拆分为：

```text
对象：ProjectGanttTask
过滤：任务类别 = 前端
层级：一级任务
动作：导出 + 总结
格式：当前甘特导出模板
范围：当前项目
结果：文件和文字报告两个产物
```

用户说“分析风险并写入登记册”时，助手必须拆分为：

```text
动作一：读取项目任务、事项和已有风险
动作二：生成候选风险及证据
动作三：展示风险字段预览
动作四：检查重复风险
动作五：请求写入授权
动作六：写入 RiskRegisterItem 和关联关系
动作七：返回写入 ID、字段和通知结果
```

### 9.3 工具调用分层

工具分为：

- 查询工具：读取对象和统计数据。
- 分析工具：排期分析、风险分析、挣值分析、资源分析。
- 产物工具：按系统模板导出 Excel、CSV、MPP、项目报告和图表。
- 草案工具：生成待确认变更，不写入数据库。
- 写入工具：新建、修改、关联、审批和删除。

写入工具的统一返回结构：

```json
{
  "status": "preview|needs_approval|applied|rejected",
  "objectType": "ProjectGanttTask",
  "objectIds": [],
  "changes": [],
  "impact": [],
  "permission": {},
  "approval": {},
  "auditId": "..."
}
```

### 9.4 思考和展示边界

助手可以流式展示可验证的工作步骤：

- 正在识别对象和范围
- 正在读取当前项目数据
- 已筛选出多少条任务
- 正在检查层级和依赖
- 正在生成文件或变更预览
- 需要用户确认的原因

不应展示模型内部不可验证的隐性推理原文，而应展示结构化的分析依据、工具调用、过滤条件、命中数量和影响清单。

## 10. 数据迁移和兼容方案

### 10.1 迁移原则

- 新表先增加，旧表不立即删除。
- 所有关联先使用 nullable 外键，完成回填和校验后再收紧约束。
- 迁移脚本必须幂等，可重复执行。
- 更新前自动备份数据库和文档。
- 生产恢复必须兼容旧版本 schema，禁止无条件删除整库。

### 10.2 现有数据映射

| 现有对象 | 新对象关系 |
|---|---|
| `Project` | 继续作为项目根对象 |
| `ProjectGanttTask` | 继续作为正式计划任务 |
| `WeeklyItem` | 迁移为项目事项语义，保留旧 ID |
| `RiskRegisterItem` | 继续作为风险对象 |
| `ProjectDocumentFile` | 增加空间和关联对象引用 |
| `ProjectMember` | 继续作为项目成员来源 |
| `ApprovalWorkflow*` | 扩展对象类型和审批效果 |
| `Assistant*` | 增加模块注册表、工具调用和产物引用 |

不允许通过修改名称来完成迁移关联；旧 ID 必须保留，显示编号可以重新生成。

### 10.3 回滚策略

- 每个迭代发布前保存数据库备份、文档备份和 schema 版本。
- 新功能使用功能开关控制。
- 数据回填失败时回滚回填，不回滚用户已经产生的无关数据。
- 结构迁移必须提供反向脚本或明确的恢复备份方案。

## 11. 分阶段实施计划

### 迭代 1：基础对象和活动流

交付：

- 模块注册表
- 对象关联规范
- 统一活动事件
- 统一通知事件
- 保存视图基础模型
- 佳佳只读动态发现

验收：

- 助手可以发现所有已注册模块、字段和查询工具。
- 删除、改名、导入和恢复都能从活动流查到结构化记录。
- 不改变现有 WBS 排期结果。

### 迭代 2：执行阶段和工时

交付：

- 阶段/工作包
- 阶段列表和看板
- 阶段引用 WBS
- 预计/已用/剩余工时
- 工作日志和人员负荷

验收：

- 阶段不产生第二套计划日期。
- 同一人员的容量冲突能在 WBS 和阶段视图中保持一致。
- 工作日志审批不改变基线。

### 迭代 3：需求、缺陷和测试

交付：

- 需求
- 缺陷
- 测试用例
- 测试执行
- 测试报告
- 多对多追踪和质量门禁

验收：

- 可从需求追到 WBS、测试和缺陷。
- 可从缺陷追到修复任务和回归测试。
- 关键缺陷和测试门禁按配置阻断或提醒。

### 迭代 4：协同、看板和文档空间

交付：

- 统一列表/看板/时间线
- 动态流、评论、@和通知
- 文档空间、版本和关联
- 阶段/需求/缺陷/测试的保存视图

验收：

- 视图只改变展示配置，不复制业务数据。
- 文件上传、关联、替换、删除和恢复均可追溯。

### 迭代 5：Agent 写入和报表

交付：

- 查询、分析、导出、草案和写入工具分层
- 意图解析和范围确认
- 权限、审批和审计统一接入
- 模板化 Excel/MPP/项目报告
- 项目、阶段、需求、缺陷和测试报表

验收：

- “导出一级任务”“导出高风险事项”“将分析风险写入登记册”等请求都能识别准确范围。
- 任何写入前都能展示对象、字段、影响和权限。
- 没有权限或审批未通过时，助手不能假装已执行。

## 12. 测试策略

### 12.1 数据一致性

- 重命名任务后，需求、缺陷、测试、事项和风险关联不丢失。
- 删除或归档对象时，所有引用都有明确策略。
- 导入、导出再导入不改变对象 ID 和层级顺序。
- 阶段汇总日期始终来自 WBS。

### 12.2 排期回归

- T0 正排、完成日期倒排、工作日、节假日和资源冲突。
- 依赖关系跨阶段、跨负责人和跨层级。
- 阶段看板操作不会改变排期。
- 进度审批不会改变基线。

### 12.3 权限回归

- 无项目权限用户不能读取项目任务、预算和文档。
- 只有负责人可以提交自己的进度和工时。
- 只有授权角色可发布/变更基线。
- 只有超级管理员可编辑审批流程和执行数据恢复。
- 助手不能通过自然语言绕过权限。

### 12.4 性能和可靠性

- 460 条以上 WBS 在列表、看板和阶段汇总中保持可用。
- 需求、缺陷、测试和任务关联使用分页和索引。
- 大批量导出使用后台任务，显示进度和失败原因。
- 备份失败、云盘失败和导入失败产生通知和审计记录。

## 13. 暂不实施的内容

为控制复杂度，以下内容暂不作为第一阶段目标：

- 完整复制禅道产品线和发布管理。
- 同时支持多种复杂依赖关系；当前正式排期继续以 FS 为主。
- 多人实时协同编辑同一 WBS 表格。
- 用禅道执行日期覆盖 PMS 的 WBS 日期。
- 未明确业务价值的插件市场和大型自定义报表引擎。

## 14. 最终决策建议

建议采用“借鉴流程、不复制系统”的路线：

1. 先建立统一对象和关联键，避免后续再出现改名导致关联消失。
2. 再增加执行阶段和工时闭环，解决日常项目管理的可用性问题。
3. 然后增加需求、缺陷和测试追踪，形成研发质量闭环。
4. 最后让佳佳通过模块注册表发现这些对象，并以权限、审批和审计为边界执行操作。

这样既能吸收禅道成熟的研发过程管理方式，又能保留 PMS 在工程排期、资源约束、关键路径、基线和挣值方面的核心能力。
