# 禅道与 Ceastar 项目管理系统差异及借鉴建议

## 1. 文档信息

- 对比日期：2026-08-23
- 禅道地址：`http://localhost:8089`
- 实测版本：禅道开源版 `22.4`
- 对比对象：当前项目管理系统（以下简称 PMS）
- 实测账号：管理员账号，仅用于本地登录查看，不写入本文档

## 2. 结论摘要

禅道和 PMS 解决的核心问题不同：

- 禅道更偏向软件研发全生命周期管理，主线是“产品/需求 -> 项目 -> 执行 -> 任务/测试/缺陷 -> 发布与统计”。
- PMS 更偏向复杂项目的计划控制，主线是“项目 -> WBS -> 依赖关系/资源 -> 正排或倒排 -> 关键路径/浮动时间 -> 基线/挣值”。

当前不建议放弃 PMS、整体迁移到禅道，也不建议把禅道的所有对象原样复制进 PMS。更合适的方向是：保留 PMS 的 WBS 和正式排期引擎，吸收禅道在研发过程对象、执行周期、需求缺陷追踪、工时记录、看板和活动流方面的设计。

优先级最高的借鉴项：

1. 增加“执行/阶段”对象，但让它引用 WBS，不再创建第二套排期。
2. 增加需求、缺陷、测试用例、测试执行、测试报告之间的可追溯关系。
3. 增加预计工时、已用工时、剩余工时和工作日志闭环。
4. 增加面向角色的仪表盘、看板、筛选视图和活动流。
5. 将这些对象纳入权限、通知、审批和佳佳智能助手的动态发现能力。

## 3. 实测范围和限制

本次使用管理员账号登录了禅道，实际浏览了导航、空态列表、创建表单和后台设置页面，没有点击保存、创建、删除或修改任何业务数据。

本地禅道实例当前没有产品、项目集、项目、执行、测试业务数据，因此下列结论基于真实可见的菜单、字段和空态页面，不假设实例中存在业务数据。

已实测页面：

- [地盘](http://localhost:8089/index.php?m=my&f=index)：欢迎总览、待处理统计、近期项目、动态和报表入口。
- [项目集](http://localhost:8089/index.php?m=program&f=browse)：项目集/项目视角、项目集看板、状态筛选和项目集创建入口。
- [产品](http://localhost:8089/index.php?m=product&f=all)：产品列表、产品看板、产品线、产品创建入口。
- [项目](http://localhost:8089/index.php?m=project&f=browse)：项目列表、项目看板、未完成/未开始/进行中筛选和项目创建入口。
- [执行](http://localhost:8089/index.php?m=execution&f=all)：执行列表、执行看板、执行状态筛选和执行创建入口。
- [测试](http://localhost:8089/index.php?m=qa&f=index)：Bug、用例、套件、测试单、测试报告、用例库和自动化。
- [文档](http://localhost:8089/index.php?m=doc&f=lastViewedSpace)：我的空间、团队空间、产品空间、项目空间和接口空间。
- [组织](http://localhost:8089/index.php?m=my&f=team)：用户、部门、职位、联系方式和用户操作入口。
- [后台](http://localhost:8089/index.php?m=admin&f=index)：系统设置、功能开关、人员管理、功能配置、通知设置、插件管理、二次开发和数据导入。

实测创建表单还确认了：

- 产品可以填写产品线、产品名称、产品类型、产品负责人、评审人和产品描述。
- 执行可以填写所属项目、执行名称、执行类型（短期/长期/运维）、计划起止日期、可用工作日、关联产品、关联计划和执行描述。
- 执行提供“简洁版/完整版”、复制执行、保存模板和应用模板。

## 4. 业务模型差异

| 领域 | 禅道 | 当前 PMS | 关键差异 |
|---|---|---|---|
| 顶层组织 | 项目集、产品、项目并列管理 | 以项目为中心 | 禅道能同时管理产品线和多个交付项目，PMS 更聚焦单项目交付计划 |
| 项目计划 | 项目下面拆分执行/迭代 | 项目直接进入 WBS 和甘特 | PMS 的层级更适合正式工程计划，禅道的执行更适合短周期研发协作 |
| 任务结构 | 执行中的任务、子任务、状态、优先级、负责人和工时 | 多层 WBS、Task ID、任务类别、描述、负责人、依赖、工期、日期、进度、工时 | PMS 的结构和排期约束更深，禅道的任务过程字段更标准化 |
| 排期方式 | 以执行周期和任务工时为主 | T0、正排、倒排、自然日/工作日、节假日、资源冲突、CPM、浮动时间 | PMS 具备正式计划计算能力，禅道不能直接替代这套引擎 |
| 依赖关系 | 任务和执行过程关联，强调研发协作 | 当前重点支持 FS，并计算关键路径和浮动 | PMS 更接近项目计划网络图，禅道更接近研发工作流 |
| 资源管理 | 负责人、团队、工时和工作日志 | 项目成员、多人父级负责人、末级任务负责人、资源排期和冲突提示 | PMS 对计划资源的约束更强，禅道对实际投入记录更成熟 |
| 需求管理 | 产品需求、计划、版本、故事/需求流转 | 项目事项、风险登记册、文档和 WBS | PMS 还缺少从需求到任务的标准追踪链 |
| 缺陷和测试 | Bug、测试用例、套件、测试单、测试报告、用例库、自动化 | 暂无独立 Bug/测试对象，风险和事项承担部分问题跟踪 | 这是当前 PMS 最大的业务空白之一 |
| 文档 | 产品空间、项目空间、团队空间、接口空间、我的空间 | 按项目文件夹和目录清单管理，支持本地/云盘方向 | PMS 的目录结构更贴近交付资料，禅道的空间和知识组织更清晰 |
| 协同 | 动态、团队、执行看板、任务过程 | 协同沟通、审批中心、佳佳助手、通知 | PMS 已有基础，但需要把对象活动统一起来 |
| 审批 | 后台和流程配置能力，结合研发对象 | 可配置审批流程、节点、实例、提交和效果 | 两者都有流程能力，PMS 更需要把 WBS/进度审批闭环做稳定 |
| 权限 | 组织、用户、分组、后台功能配置，并按研发对象控制 | 后台账号、项目角色/人员、模块权限和项目级权限 | 禅道的组织权限模型更完整，PMS 的项目级权限更贴合交付场景 |
| 报表 | 地盘统计、BI、看板、测试报告和动态 | 挣值分析、关键路径、甘特图、备份历史和助手导出 | PMS 的项目控制指标更深，禅道的研发过程统计更丰富 |
| AI | 有独立 AI 导航入口 | 佳佳支持查询、分析、导出、计划和受控 Agent 操作 | PMS 的助手更贴近项目数据，应重点补强对象识别和工具编排，而不是只增加聊天入口 |
| 数据保护 | 后台包含备份、安全、通知和扩展配置 | PostgreSQL、数据库/文档备份、恢复、更新脚本和部署包 | PMS 对内网部署和数据迁移的要求更高，当前能力不应删减 |

## 5. 当前 PMS 已有的优势

以下能力是当前 PMS 的核心差异化能力，不应因为借鉴禅道而弱化：

1. **WBS 结构和任务 ID**：支持父子层级、任务类别、层级调整、拖拽排序和批量操作。
2. **正式排期模型**：支持 T0 方式、工期固定正排、工期固定倒排，以及自然日/工作日和节假日规则。
3. **网络计划能力**：支持紧前任务、资源冲突、关键路径、总浮动和自由浮动的计算与可视化。
4. **基线控制**：支持计划确认、基线、变更影响、进度提交与审批的扩展方向。
5. **项目控制指标**：已有挣值分析、PV/EV/AC、进度和成本绩效相关模型。
6. **交付资料管理**：文档清单按项目目录组织，并考虑本地目录和公司云盘。
7. **内网部署安全**：面向 PostgreSQL、Windows Docker、备份恢复和版本更新，不依赖禅道的部署方式。

这些能力直接对应用户当前的工程计划场景，禅道的产品/执行模型不能直接替代。

## 6. 禅道最值得借鉴的能力

### 6.1 高价值：增加执行/阶段对象

禅道把项目进一步拆成“执行”，执行有自己的名称、类型、计划起止日期、可用工作日、关联产品和关联计划，并提供执行列表与看板。

建议在 PMS 中增加一个轻量的“项目执行/阶段”对象：

- 一个项目可以有多个阶段，例如需求、设计、采购、样机、量产、验收。
- 阶段可以引用一组 WBS 任务，但不能复制任务，也不能独立产生第二套开始/完成日期。
- WBS 仍是唯一的计划事实来源；阶段只保存范围、负责人、状态、视图和统计口径。
- 阶段可有短期/长期/运维等类型，但不改变正式排期算法。
- 阶段应支持列表、看板、阶段进度、风险、审批和文档入口。

验收标准：同一任务在 WBS、阶段看板和助手查询中只能有一个任务 ID、一个计划日期来源；阶段切换不能产生日期分叉。

### 6.2 高价值：建立需求/缺陷/测试追踪链

禅道将产品、需求、任务、Bug、测试用例、测试单和测试报告分开。PMS 当前有事项、风险和 WBS，但没有完整的质量闭环。

建议增加以下可选对象：

```text
需求/交付要求 -> WBS任务 -> 测试用例 -> 测试执行 -> 测试报告
                         \-> 缺陷 -> 修复任务 -> 回归结果
```

设计要求：

- 对象之间使用数据库 ID 关联，显示名称仅用于展示。
- 需求可以关联多个 WBS 任务，任务也可以覆盖多个需求。
- 缺陷必须有状态、严重程度、负责人、发现版本、修复版本和回归结果。
- 缺陷修复后可以关联一个或多个 WBS 任务，但不能改变原任务名称来维持关系。
- 风险仍然保留为项目不确定性管理，不把 Bug 直接当成风险。

### 6.3 高价值：工时闭环

禅道的执行表单和后台扩展入口都体现了“预计工时、已用工时、剩余工时、每天最大工时”这一类过程数据的重要性。

建议在 PMS 中把以下字段和流程标准化：

- 预计工时：排期时由工期和每日工时计算，也允许在受控范围内调整。
- 已用工时：由负责人提交实际投入，不由计划日期反推。
- 剩余工时：由负责人更新或按审批后的进度辅助计算。
- 工作日志：按任务、人员、日期记录，支持审批和审计。
- 资源容量：按人员、角色、工作日历和请假/不可用时间计算。

这会让“计划偏差”和“投入偏差”分开，避免只看日期却无法解释成本和资源变化。

### 6.4 高价值：看板、动态和多视图

禅道在多个模块提供列表、看板、状态筛选、搜索和近期动态入口。PMS 已有甘特图、列表、审批和助手，但还需要统一视图层。

建议每个核心对象统一提供：

- 列表视图：适合批量编辑和筛选。
- 看板视图：按状态、阶段、负责人或风险等级分列。
- 时间视图：只对具备计划日期的对象显示甘特/时间线。
- 动态流：记录谁在何时修改了什么、审批了什么、导入了什么。
- 保存视图：保存筛选条件、列显示、排序和权限范围。

重点是复用同一查询模型，不为每个视图复制一套业务数据。

### 6.5 中高价值：产品/项目集层级

禅道的项目集和产品入口能表达“同一产品有多个交付项目”以及“多个项目属于一个项目集”。

如果 PMS 后续管理多个产品或多个批次，建议增加：

- 产品/设备型号
- 产品线
- 项目集/客户群
- 项目与产品的多对多关联

这类对象应位于项目之上，不能替代项目 WBS。当前单项目使用时可以隐藏，避免增加操作负担。

### 6.6 中价值：文档空间与知识沉淀

禅道提供我的空间、团队空间、产品空间、项目空间和接口空间。PMS 的文档清单更强调目录与上传归档，可以借鉴“空间”概念：

- 项目交付空间：合同、立项、计划、验收等正式资料。
- 研发空间：需求、设计、接口、测试资料。
- 团队空间：制度、模板、操作手册。
- 文档版本、评论、关联任务和关联审批。

仍然由 PMS 的本地目录/公司云盘配置负责物理存储，空间只负责权限和业务分类。

### 6.7 中价值：权限、通知和后台配置

禅道后台页面明确分出系统设置、功能开关、人员管理、功能配置、通知设置、插件管理、二次开发和数据导入。

PMS 可以借鉴这种后台分区：

- 系统策略：日历、工时、备份、存储、导入导出。
- 组织权限：账号、角色、项目成员、审批人。
- 模块开关：按部署场景启用/隐藏需求、测试、执行、AI 等模块。
- 通知规则：任务变更、基线变更、审批、备份失败、风险升级。
- 审计和导入：所有批量导入、导出、恢复和权限变更可追溯。

### 6.8 低到中价值：AI 入口和助手编排

禅道有独立 AI 导航入口，PMS 已有佳佳智能助手和受控 Agent。可借鉴的是入口和上下文分层，不是简单复制聊天页面：

- 助手应能识别当前产品、项目、阶段、WBS、需求、缺陷和测试对象。
- 先生成意图和数据范围，再调用查询/导出/写入工具。
- 导出前展示对象类型、层级范围、过滤条件、命中条数和文件格式。
- 写入前展示变更计划、影响、权限和审批要求。
- 工具名称、参数和结果都进入可回溯的操作记录。

## 7. 不建议直接照搬的部分

1. **不要把执行当成第二套甘特计划**：阶段日期只能来自 WBS 汇总，否则会出现两个计划事实来源。
2. **不要把产品、需求、事项、风险、Bug 混为一个表**：它们的生命周期和责任边界不同，应通过关联表连接。
3. **不要用禅道的任务状态替代正式排期状态**：任务“进行中”不等于计划可以移动，计划变更仍需遵守基线和审批规则。
4. **不要为了仿照菜单而一次性增加大量模块**：没有实际业务数据和流程时，应按模块开关逐步启用。
5. **不要削弱当前的备份、恢复、数据库兼容和 Windows 内网部署能力**：这些是 PMS 的实际部署约束，禅道的界面层不能解决。

## 8. 建议的实施顺序

### 第 0 阶段：统一术语和关联键

- 固定项目、阶段、WBS 任务、事项、风险、需求、缺陷、测试用例的实体边界。
- 所有关联使用不可变数据库 ID，任务 ID、名称只作为展示字段。
- 规定删除、归档、恢复和跨模块引用时的级联/置空/阻断规则。
- 为助手提供可检索的模块注册表、字段字典和权限字典。

### 第 1 阶段：执行/阶段和工时

- 增加项目阶段对象和阶段看板。
- 阶段只引用 WBS 任务，不存第二套计划日期。
- 增加已用工时、剩余工时、工作日志和人员容量视图。
- 任务甘特、阶段看板、人员负荷使用同一查询接口。

### 第 2 阶段：需求、缺陷和测试

- 增加需求、Bug、测试用例、测试执行和测试报告。
- 建立需求-WBS-Bug-测试的多对多追踪。
- 增加质量门禁：关键缺陷未关闭时不能提交验收或发布基线。
- 将风险登记册保留为风险管理，不替代质量缺陷。

### 第 3 阶段：协同、通知和报表

- 统一动态流、评论、@提醒、审批通知和待办/通知中心。
- 增加列表、看板、甘特、统计仪表盘和保存视图。
- 让基线变更、排期冲突、进度审批、备份失败都能进入通知中心。

### 第 4 阶段：佳佳 Agent 适配新模块

- 助手启动时读取模块注册表和字段字典，而不是只依赖固定提示词。
- 对“导出、生成报告、写入风险、更新任务”等请求强制先做意图解析和范围确认。
- 输出工具调用、数据范围、过滤条件、影响评估和结果摘要。
- 新增模块只需注册查询、导出、写入、审批工具，助手即可发现；涉及写入的工具仍受权限和审批控制。

## 9. 对当前 PMS 的具体改进清单

| 优先级 | 改进项 | 目标 |
|---|---|---|
| P0 | 执行/阶段引用 WBS | 解决阶段管理缺失，同时避免重复排期 |
| P0 | 需求-Bug-测试追踪 | 建立从业务要求到交付验证的闭环 |
| P0 | 工时和工作日志 | 解释资源冲突、进度偏差和成本偏差 |
| P0 | 统一对象活动流 | 让变更、审批、通知和协同可回溯 |
| P1 | 看板/保存视图 | 降低甘特图之外的日常使用成本 |
| P1 | 项目集/产品线 | 支持多个项目和多个设备型号的组合管理 |
| P1 | 文档空间和版本 | 让交付文档、研发资料和模板有清晰归属 |
| P1 | 测试质量门禁 | 将缺陷和测试结果接入发布/验收流程 |
| P2 | BI/自定义报表 | 补足多项目经营和管理层分析 |
| P2 | 插件/模块开关 | 让内网部署按业务场景启用功能 |

## 10. 最终建议

当前 PMS 不适合被禅道整体替换：你的核心需求是工程 WBS、资源约束、依赖关系、关键路径、T0 正倒排、基线和挣值，这些能力已经成为 PMS 的核心资产。

最稳妥的产品方向是：

```text
禅道的研发过程组织方式
        +
PMS 的正式项目计划和资源计算引擎
        +
统一的需求/任务/缺陷/测试/文档/审批关联
        +
可以读取动态模块和字段的佳佳 Agent
```

第一步建议实施“执行/阶段 + 工时闭环”，第二步实施“需求/缺陷/测试追踪”，第三步再做看板和报表。这样能直接改善日常使用体验，同时不会破坏现有 WBS 和排期数据。

## 11. 证据与后续边界

- 本文中关于禅道菜单、版本、字段和空态的描述来自 2026-08-23 在本地禅道实例中的实际页面检查。
- 当前实例没有业务数据，因此没有对创建后的完整项目、执行、任务、测试和审批流做写入测试。
- 下一步如要继续实施，应先用一份非生产测试项目验证对象关联和权限，不应直接把禅道数据写入当前 PMS 生产数据库。
