# 项目级授权与执行 Gate 原子提交

## Context

项目管理 API 同时依赖全局权限树和项目成员范围。过去两类校验分散在路由中，部分项目接口只校验全局权限，助手读取路径还维护了独立的项目访问函数。执行 Gate 申请还将 Gate、审批实例、Gate 状态和操作历史拆成多个提交边界，审批启动失败时可能留下孤立的 Gate 记录。

## Decision

- 使用 `src/lib/project-authorization.ts` 作为项目 API 的统一授权门面。
- 项目访问必须同时满足全局权限和项目成员范围；管理员角色继续通过既有管理员规则获得项目访问。
- 保留路由已有的权限错误语义和动态权限组合，先在统一门面后补项目范围校验，再逐步迁移为完整的 `requireProjectPermission` 调用。
- `startApprovalWorkflow` 支持接收现有 Prisma 事务客户端；执行 Gate 申请在同一个事务中完成 Gate 创建、审批实例创建、Gate 状态更新和操作历史写入。
- 权限树在同一请求用户对象的生命周期内共享一次查询 Promise，不跨请求缓存权限配置。

## Consequences

- 新增项目 API 必须使用统一授权门面，不得直接引入助手专用项目访问别名。
- Gate 申请失败不会保留半成品 Gate，但事务中包含的默认审批流程初始化也会与本次申请共享提交边界。
- 权限配置变更不需要清理长期缓存；每个新请求仍读取最新配置。
- 后续模块化迁移可将该门面移动到 `identity-access` 模块，并以兼容转发保持旧导入路径。

## Rejected alternatives

- 不采用全局内存权限缓存：会产生配置变更延迟和多实例不一致。
- 不采用 Gate 创建后再异步启动审批：会扩大孤立状态窗口，且不满足审批申请的一致性要求。
