# Ceastar PMS 功能模块说明与业务关联

> 适用对象：需要快速了解系统能力的管理层、项目经理、项目成员和实施人员。
>
> 阅读目标：先知道每个模块“解决什么问题”，再理解它们如何把一个项目从立项、计划、执行一直管理到验收和归档。

## 1. 一句话理解系统

Ceastar PMS 是一套以**项目为中心**的管理系统。它把人员、计划、任务、风险、费用、交付物、审批和沟通放在同一项目上下文中，让项目从“有目标”变成“有计划、有人做、有证据、可管控、可复盘”的完整闭环。

可以把系统理解为一条项目管理流水线：

```text
账号与权限
    ↓
创建项目、指定成员、明确合同目标
    ↓
用 WBS 拆解范围、工期、负责人和依赖关系
    ↓
形成执行阶段和门禁，按计划推进
    ↓
事项催办 + 风险处置 + 文档交付 + 预算控制
    ↓
关键动作进入审批；问题在协同中闭环
    ↓
挣值和驾驶舱评价项目绩效
    ↓
项目完成、资料归档、审计留痕、备份恢复
```

其中，“项目主数据、权限、审批、协同、日志与备份”贯穿全部模块；它们不是孤立的功能，而是保证项目可控、可追溯的基础设施。

## 2. 系统模块总览

| 模块 | 主要回答的问题 | 典型使用者 | 主要产出 |
| --- | --- | --- | --- |
| 账号、角色与权限 | 谁能看、谁能改、谁能批？ | 系统管理员、项目经理 | 可控的访问范围与岗位职责 |
| 项目信息管理 | 这个项目是什么、由谁负责、处于什么状态？ | 项目经理、管理层 | 项目档案、成员名单、项目生命周期 |
| 项目经营驾驶舱 | 组织当前有哪些项目，整体健康度如何？ | 管理层、项目经理 | 项目分布、待办与经营概览 |
| WBS 与项目进度 | 项目具体要做什么、何时完成、谁负责？ | 项目经理、项目成员 | 计划树、甘特图、依赖关系、基线 |
| 项目执行驾驶舱 | 当前正推进到哪个阶段，能否进入下一阶段？ | 项目经理、阶段负责人 | 阶段看板、执行预警、Gate 门禁 |
| 项目事项管理 | 今天需要推动或解决哪些具体问题？ | 项目成员、项目经理 | 可跟踪的事项清单与处理记录 |
| 风险登记册 | 哪些不确定因素可能影响目标，如何应对？ | 项目经理、风险责任人 | 风险台账、影响分析、处置措施 |
| 项目预算管理 | 钱花在哪里，成本与收益是否可控？ | 项目经理、财务或经营人员 | 预算结构、成本及收益汇总 |
| 文档清单管理 | 交付物、过程材料和依据文件在哪里？ | 项目成员、项目经理 | 按阶段归档的项目文档 |
| 项目绩效（挣值） | 进度和成本表现是否符合计划？ | 管理层、项目经理 | PV、EV、AC、偏差与预测指标 |
| 审批中心与待办 | 哪些关键动作需要决定、由谁决定？ | 审批人、项目经理 | 审批记录、待办、流程版本 |
| 协同沟通 | 围绕项目或审批如何留痕讨论？ | 全体项目相关人员 | 主题、消息、@ 提及和附件 |
| 智能助手 | 如何快速查询项目情况、生成建议或执行受控操作？ | 获授权用户 | 基于权限的问答、建议与操作预览 |
| 系统数据管理与运维 | 如何保证数据安全、可恢复、可审计？ | 系统管理员 | 备份、恢复、事件日志与清理记录 |

## 3. 各模块详细说明

### 3.1 账号、角色与权限：先确定“谁能做什么”

**模块目标**：让每名用户只接触与其岗位和项目责任相匹配的数据与操作，避免“所有人都能改所有内容”。

**核心功能**：

- 后台账号管理：新增、停用、维护系统用户账号。
- 角色与人员配置：为角色配置菜单和操作权限，并为项目安排成员。
- 项目级访问控制：用户是否能查看某个项目，不只取决于系统角色，也取决于其是否被加入该项目。
- 菜单按权限显示：无权限的功能不会作为可操作入口展示。
- 管理员边界：部分系统设置、账号和系统数据能力仅由系统管理员使用。

**输入与输出**：

- 输入：账号、角色、权限配置、项目成员关系。
- 输出：各用户在项目、审批、文档、智能助手等模块中的可见范围和可执行动作。

**与其他模块的关系**：

- 它是所有模块的共同入口。项目成员决定了 WBS 负责人、事项责任人、风险责任人和协同参与者的可选范围。
- 审批流程根据岗位、角色或配置的审批人路由；智能助手也只能读取用户本来就有权限查看的数据。

**对外讲解时可以这样说**：系统不是“给所有人一张项目表”，而是先定义职责，再让每个人在自己负责的范围内协作。

### 3.2 项目信息管理：建立项目的唯一业务档案

**模块目标**：把项目的商业背景、目标边界、负责人和生命周期统一起来，作为后续计划、预算、文档和审批的共同归属。

**核心功能**：

- 创建和维护项目名称、编码、客户、合同金额、计划起止日期等基础信息。
- 指定项目经理并维护项目成员。
- 管理项目状态，例如启动、完成、作废和恢复。
- 对重要状态改变发起审批，避免项目被随意启动、结项或撤销。
- 在移除成员时识别其已关联的任务、事项和风险，帮助项目经理完成责任交接。

**输入与输出**：

- 输入：合同或立项信息、客户信息、项目经理、成员名单、目标日期。
- 输出：项目 ID、项目边界、可参与人员，以及所有项目级数据的归属容器。

**与其他模块的关系**：

- WBS、预算、文档、执行阶段、事项、风险、绩效分析都必须挂在一个项目之下。
- 合同金额和项目日期为预算与排期提供经营和时间边界。
- 项目状态会影响后续可编辑性：已完成或已作废项目不应再继续产生常规执行数据。

**示例**：在“智能仓储能耗优化示范项目”中，先登记客户、合同金额、项目经理和核心成员，才可以继续制定 WBS、建立预算和上传验收材料。

### 3.3 项目经营驾驶舱：从项目组合看经营全貌

**模块目标**：让管理者不必逐个点开项目，就能了解项目分布、近期事项和整体工作负荷。

**核心功能**：

- 查看项目列表和项目基本经营信息。
- 汇总项目分布、本月事项和本周事项等信息。
- 快速进入具体项目，定位需要重点关注的对象。
- 提供跨项目的 WBS 概览入口，便于从计划维度观察整体进展。

**输入与输出**：

- 输入：项目档案、WBS、事项等已沉淀的数据。
- 输出：面向管理层的整体视图和需要跟进的项目入口。

**与其他模块的关系**：

- 驾驶舱不重复录入数据，而是汇总项目、计划、事项等模块的结果。
- 当驾驶舱发现异常时，管理者可下钻到项目执行、事项、风险、预算或绩效模块追溯原因。

### 3.4 WBS 与项目进度：把目标拆成可执行的计划

**模块目标**：把“要完成一个项目”的大目标，分解为阶段、工作包和具体任务，并明确负责人、工期、前后依赖和完成标准。

**核心功能**：

- 用树形 WBS 分层管理工作范围，支持新增、调整层级、排序、复制、剪切和删除等结构操作。
- 为任务维护负责人、计划开始/结束、工期、工作量、完成百分比和备注等计划信息。
- 通过甘特图展示时间轴，直观看到任务安排和相互影响。
- 维护 FS（完成—开始）等业务依赖关系，避免后续任务早于前置工作启动。
- 支持自动排程、固定工期正排、倒排和固定日期等计划方式。
- 考虑负责人日容量、任务依赖、项目边界和资源冲突，形成可执行而非“纸面好看”的排期。
- 支持导入、导出、导入预览和疑似任务匹配，降低从外部计划迁移的成本；二进制 MPP 导出依赖已配置的转换服务。
- 支持网络图、关键路径/资源关键链分析和进度/资源排程分析。
- 支持 WBS 基线：草案经过审批发布后冻结，形成后续偏差比较的正式计划依据。
- 支持模块级撤销/重做和历史快照，方便纠正计划调整。

**输入与输出**：

- 输入：项目目标、成员、合同日期边界、工作范围、资源假设和任务依赖。
- 输出：可执行任务计划、负责人分工、基线版本、关键路径和执行进度来源。

**与其他模块的关系**：

- WBS 是执行驾驶舱的主要计划来源：一级 WBS 可自动生成执行阶段。
- 事项通常关联具体任务；风险可反向标识它影响哪些任务；这些信息又会回到执行驾驶舱形成预警。
- WBS 的计划值、实际工作与完成百分比是挣值分析的主要计算基础。
- 关键计划变更和基线发布通过审批留下正式决策记录。

**对外讲解时可以这样说**：WBS 不只是甘特图。它既是“工作分解表”，也是执行、风险、绩效和审批共同使用的项目主计划。

### 3.5 项目执行驾驶舱与 Gate：把计划变成阶段化执行

**模块目标**：让项目经理从“看很多任务”转变为“按阶段管理结果”，及时判断项目是否满足进入下一阶段的条件。

**核心功能**：

- 手工创建执行阶段，或根据一级 WBS 自动生成阶段。
- 为阶段维护名称、负责人、日期范围和说明。
- 聚合展示每个阶段下的 WBS、事项和风险，形成阶段级工作全景。
- 基于进度、事项和风险显示执行预警，帮助发现卡点。
- 提供 Gate 门禁申请：当阶段达到既定准入条件时，发起放行审批，获批后才能进入下一管理节点。

**输入与输出**：

- 输入：WBS 一级结构、任务进度、事项状态、风险状态、阶段准入条件。
- 输出：阶段看板、预警信息、Gate 放行记录和阶段决策。

**与其他模块的关系**：

- 它承接 WBS 的计划结构，把细粒度任务汇总为管理层更容易判断的阶段。
- 它读取事项和风险，避免“计划显示正常，但现场问题已经堆积”的盲区。
- Gate 申请进入审批中心，审批意见与结果再回写为阶段是否可推进的依据。
- 阶段可以成为文档目录和交付物归档的自然分类方式。

### 3.6 项目事项管理：把日常推进工作明确到责任人

**模块目标**：管理计划执行中需要跟进、协调、解决或决策的具体事项，防止问题只停留在聊天记录里。

**核心功能**：

- 建立事项 ID、名称、责任人、优先级、当前问题或措施、依赖条件、备注等信息。
- 将事项关联到 WBS 任务，使事项知道“为哪项计划工作服务”。
- 将事项关联到风险，记录风险状态和处置上下文。
- 支持事项的新增、编辑、删除、结构调整、拖动排序和模块级撤销/重做。
- 支持导出，便于周会、例会和对外汇报。

**输入与输出**：

- 输入：执行中发现的问题、行动项、责任人、关联任务和相关风险。
- 输出：有负责人、有优先级、有措施的待推进事项清单。

**与其他模块的关系**：

- 事项挂靠 WBS，保证日常动作不会脱离项目计划。
- 事项可挂靠风险：风险不能只停留在登记册中，而要落实为要解决的行动项。
- 事项被执行驾驶舱汇总，用于判断阶段健康度；需要升级决策时，可以在协同模块发起讨论或进入审批。

### 3.7 风险登记册：把不确定性变成可管理的对象

**模块目标**：提前识别可能影响范围、进度、成本或质量的风险，并将风险落实到受影响的工作和应对措施上。

**核心功能**：

- 建立风险 ID、名称、等级、详细描述、责任信息和处置内容。
- 一个风险可关联多个项目事项；系统据此识别受影响的 WBS 任务。
- 通过表格和结构操作维护风险台账，支持编辑、排序、拖动和撤销/重做。
- 让风险从“风险清单”进入“执行预警与行动跟踪”。

**输入与输出**：

- 输入：风险来源、影响评估、责任人、关联事项和缓解措施。
- 输出：风险台账、受影响任务范围、风险状态和处置线索。

**与其他模块的关系**：

- 风险通过关联事项连接 WBS，因此可以回答“这个风险具体影响计划中的哪几项工作”。
- 未关闭的高风险会被执行驾驶舱作为阶段预警的重要依据。
- 风险应对可能产生预算调整、计划调整、文档证据或审批需求。

**对外讲解时可以这样说**：风险模块不只是“红黄绿列表”，它会落到具体事项和具体计划任务上，方便判断影响并推动处置。

### 3.8 项目预算管理：把经营目标分解为可控制的费用结构

**模块目标**：让项目经理既看得到合同金额和总体收益，也看得清钱准备花在哪些类别、哪些条目上。

**核心功能**：

- 汇总合同金额、成本、利润和利润率等经营指标。
- 使用层级化预算分类和预算条目管理成本结构。
- 支持费率类、共享类、评审类、风险类等预算参数或费用类别的维护。
- 支持插入、复制、剪切、移动、编辑、删除等表格操作，以及模块级撤销/重做。

**输入与输出**：

- 输入：合同金额、成本估算、费用分类、费率和风险准备等经营假设。
- 输出：预算结构、成本与收益汇总，为经营判断提供依据。

**与其他模块的关系**：

- 合同金额来自项目信息；项目时间与工作范围来自 WBS。
- 风险模块可提示需要预留的风险应对资源，WBS 变更也可能引发预算复核。
- 预算与实际执行数据共同为绩效分析提供经营视角；当发生重大调整时，可通过审批固化决策。

**边界说明**：预算模块关注项目成本与收益的计划和管理结构；具体会计核算、付款和报销流程是否由本系统承载，应以组织实际集成为准。

### 3.9 文档清单管理：沉淀过程证据与最终交付物

**模块目标**：按项目和阶段统一保存方案、设计资料、会议纪要、测试记录、验收材料等文件，确保资料可查、可下载、可交接。

**核心功能**：

- 按阶段或文件夹建立项目文档目录。
- 支持批量上传、下载和删除文档；单文件上传上限为 20 MB。
- 文档可存放在系统本地存储或企业 WebDAV 云盘。
- 已完成或已作废的项目停止常规上传，保护结项资料的完整性。

**输入与输出**：

- 输入：项目过程文件、交付物、审批依据、沟通附件。
- 输出：与项目阶段相对应、可追溯的文档资产。

**与其他模块的关系**：

- 文档可按执行阶段归类，成为 Gate 评审和项目验收的证据。
- 审批、协同中的附件可为文档管理补充上下文；项目完成后形成可归档的项目资料集。
- 项目恢复时会进行文档存在性等预检查，避免只恢复业务数据而丢失资料关系。

### 3.10 项目绩效（挣值分析）：同时看进度和成本表现

**模块目标**：用统一指标判断“做了多少工作、花了多少资源、是否偏离计划”，避免仅凭主观感受判断项目好坏。

**核心功能**：

- 计算并展示 PV（计划价值）、EV（挣得价值）、AC（实际成本）。
- 提供 SV、CV、SPI、CPI、EAC、ETC、VAC、TCPI 等进度与成本偏差、预测指标。
- 支持按项目计划和实际执行数据观察趋势，辅助管理层决策。
- 具备 MPP 计划导入/导出相关能力，便于与既有计划工具衔接。

**输入与输出**：

- 输入：WBS 计划、任务完成百分比、实际工作或成本等执行数据，以及预算或成本口径。
- 输出：进度偏差、成本偏差、效率指数和完工预测。

**与其他模块的关系**：

- WBS 提供计划与完成进度，预算和实际执行提供成本视角。
- 执行驾驶舱与经营驾驶舱可据此识别需要管理层关注的项目或阶段。
- 当绩效异常时，项目经理会回到事项、风险、WBS 或预算模块制定纠偏动作，并在必要时提交审批。

**边界说明**：当前挣值指标覆盖 PV 至 TCPI 等项目控制指标，不以 EMV 或三点估算作为该模块的核心范围。

### 3.11 审批中心、流程配置与待办：让关键决定有授权、有记录

**模块目标**：将启动项目、完成项目、WBS 基线发布、Gate 放行等关键动作置于规范流程中，明确由谁决定、何时决定、决定结果是什么。

**核心功能**：

- 审批中心集中查看待处理、已通过、已退回、已拒绝或已撤销的审批实例。
- 审批人可通过、退回、拒绝或撤销；退回、拒绝和撤销需要填写意见，避免无理由的流程中断。
- 管理员可为不同业务配置审批流程，管理草稿、版本和发布状态。
- 已发起的审批实例保留其当时使用的流程快照，流程后来修改不会篡改历史审批。
- 支持审批委托、审批分析和提醒能力。
- 待办与通知将需要处理的审批和项目动作集中提醒给相关人。

**输入与输出**：

- 输入：业务动作（如项目状态变更、基线发布、Gate 申请）、流程配置、审批意见。
- 输出：已授权的业务结果、意见记录、待办状态和可审计的流程历史。

**与其他模块的关系**：

- 项目生命周期、WBS 基线和执行 Gate 等模块将关键节点送入审批。
- 审批结果反过来控制项目是否启动/完成、计划是否成为基线、阶段是否允许放行。
- 协同模块可围绕审批创建主题，附件和讨论为审批意见提供依据。

### 3.12 协同沟通：让讨论与项目对象绑定并可追溯

**模块目标**：把项目讨论从零散即时消息中沉淀出来，使后来接手的人也能理解问题背景、参与者和最终结论。

**核心功能**：

- 围绕项目或审批创建协同主题。
- 在线发送消息、@ 提及成员、上传和下载附件。
- 维护已读状态，支持主题关闭。
- 通过事件机制刷新消息和通知，帮助参与者及时看到更新。

**输入与输出**：

- 输入：讨论主题、消息、参与人、附件、待确认问题。
- 输出：可检索的沟通记录、明确的结论和需要落实的行动线索。

**与其他模块的关系**：

- 项目成员来自项目信息和权限模块。
- 协同可以围绕审批实例开展，也可以针对执行问题、风险或文档进行讨论。
- 沟通结论可转为事项；重要附件可纳入文档清单，重要决策进入审批。

### 3.13 智能助手：在权限边界内提高查询和执行效率

**模块目标**：让用户用自然语言快速了解项目、生成建议或发起受控操作，同时保持项目数据和权限安全。

**核心功能**：

- 支持数据库查询、模型问答、知识库检索、模型与知识库结合，以及 Agent 等工作模式。
- 仅查询当前用户有权限访问的数据。
- 支持受白名单约束的工具操作；对有影响的操作提供预览、确认和执行记录。
- 提供授权模式、模型与嵌入模型配置、RAGLite 知识库设置、本地服务管理、聊天记录和使用偏好设置。
- 对模型输出采用规则校验与服务端验证，不把模型文本直接作为数据库写入参数。

**输入与输出**：

- 输入：用户问题、授权模式、可访问项目数据、知识库资料、受控工具请求。
- 输出：项目摘要、分析建议、待确认的操作方案、执行痕迹或导出材料。

**与其他模块的关系**：

- 智能助手读取项目、WBS、事项、风险、预算、审批等已有数据，帮助用户快速定位信息。
- 它不能绕过账号与权限；需要改变业务数据时，仍受白名单工具、确认机制和服务端权限检查约束。
- 它可帮助整理协同内容或生成分析，但最终的业务决策仍由项目角色和审批流程负责。

### 3.14 系统数据管理、日志、备份与恢复：守住数据安全底线

**模块目标**：确保项目数据在长期运行、人员交接、误操作或系统迁移后仍可追溯、可恢复、可维护。

**核心功能**：

- 系统全量备份、备份历史查看、PostgreSQL `.dump` 文件导入恢复和服务端备份目录配置。
- 支持定时备份；在已配置 WebDAV 的情况下，可每 6 小时自动备份并同步至云盘。
- 支持项目级恢复预检查，识别成员映射、文档缺失和关系冲突等风险；恢复前可保留保护性快照。
- 记录系统事件日志，固定保留 180 天；可按规定导出，并按策略进行容量清理。
- 数据清理属于不可逆操作，需要以管理制度和备份策略为前提。

**输入与输出**：

- 输入：业务数据、备份策略、WebDAV 配置、恢复文件、系统操作事件。
- 输出：可恢复的备份副本、恢复预检查结果、审计日志和运维证据。

**与其他模块的关系**：

- 该模块保护所有业务模块的数据，而不是单独服务于某个页面。
- 审批记录、项目资料、计划基线、风险事项和沟通记录都可以通过备份和日志获得长期可追溯性。
- 项目完成后的归档价值，只有在文档、备份和日志共同存在时才真正成立。

## 5. 关键关联关系说明

| 上游模块 | 连接到下游模块 | 连接方式 | 管理价值 |
| --- | --- | --- | --- |
| 账号、角色与权限 | 全部模块 | 用户身份、角色权限、项目成员关系 | 防止越权，明确责任边界 |
| 项目信息 | WBS、预算、文档、风险、事项、绩效 | 共同的项目归属、成员和时间/合同边界 | 保证所有数据属于同一项目且口径一致 |
| WBS | 执行驾驶舱 | 一级 WBS 可作为阶段来源；任务进度用于阶段汇总 | 从细任务上升到阶段管理 |
| WBS | 事项、风险 | 事项关联任务；风险通过事项识别受影响任务 | 将问题与风险落到具体计划工作 |
| WBS | 挣值分析 | 提供计划、实际与完成百分比等基础数据 | 量化进度和成本偏差 |
| 执行驾驶舱 | 审批中心 | Gate 放行申请进入审批 | 防止阶段未达标就推进 |
| 事项 | 风险、协同、执行驾驶舱 | 事项承接风险措施和沟通结论，并进入预警 | 让问题有人跟、有进展、有升级路径 |
| 风险 | 预算、WBS、执行驾驶舱 | 风险影响计划、可能需要资源预留，并触发预警 | 提前管控不确定性 |
| 文档 | 执行阶段、审批、协同 | 作为阶段交付物、评审依据和沟通附件 | 形成可验收、可交接的证据链 |
| 预算 | 项目经营、绩效、审批 | 合同金额、成本与收益形成经营视角；重大调整可审批 | 同时管理“能不能做完”和“做得是否划算” |
| 审批 | 项目状态、基线、Gate | 对关键节点授予或拒绝业务效力 | 让关键决定可追责、可追溯 |
| 协同 | 事项、文档、审批 | 讨论转行动项，附件转资料，结论支持审批 | 不让沟通停留在聊天工具里 |
| 智能助手 | 业务模块 | 在现有权限和工具边界内查询、分析、建议 | 降低查数与整理信息的时间成本 |
| 日志、备份、恢复 | 全部模块 | 记录操作、保护数据、支持恢复 | 满足长期运行与审计要求 |

## 6. 一个完整项目如何在系统中闭环

以下以“智能仓储能耗优化示范项目”为例，说明用户实际会怎样使用系统。

### 第一步：立项并组建项目团队

项目经理建立项目，填写项目编码、客户、合同金额和计划完成时间；再把方案、算法、实施和验收相关成员加入项目。此时，项目有了统一档案、责任人和访问范围。

### 第二步：制定可执行的 WBS 计划

项目经理将目标拆成“现场调研与方案确认”“设备数据接入与模型部署”“节能策略联调与验收”等一级工作包，再继续拆成具体任务。每个任务指定负责人、工期、依赖关系和完成规则；必要时通过排程功能检查资源冲突。计划确认后，发起 WBS 基线审批。

### 第三步：建立阶段并开始执行

系统可根据一级 WBS 建立执行阶段。项目经理在执行驾驶舱看到每个阶段的任务、事项和风险汇总，从而不必逐条翻任务，也能判断“当前卡在哪里”。

### 第四步：把问题和风险落实为行动

例如，发现现场传感器数据缺失：

1. 新建一条事项，关联“设备数据接入”任务，指定接口工程师和完成时限；
2. 如果该问题可能导致联调延期，同时登记“现场数据完整性不足”风险，并把该事项关联为应对措施；
3. 在协同主题中 @ 现场负责人和客户接口人，上传沟通记录；
4. 执行驾驶舱据此对该阶段发出关注或预警。

这样，问题、风险、计划和沟通不是四套散乱记录，而是同一条责任链。

### 第五步：控制成本和交付物

在预算中维护设备接入、实施服务、评审和风险预留等费用结构；将方案、测试记录、验收材料按阶段上传至文档清单。若范围或风险导致成本、工期发生重大变化，项目经理调整相关计划和预算，并按组织规则发起审批。

### 第六步：在关键节点进行 Gate 决策

当“数据接入与模型部署”阶段的任务、问题和交付物满足准入条件时，项目经理发起 Gate 放行申请。审批人审核阶段证据、风险和结论；通过后项目进入下一阶段，退回后则继续处理未满足项。

### 第七步：用绩效数据判断是否需要纠偏

项目经理在挣值分析中查看计划价值、完成价值和实际成本。如果发现进度或成本偏差，就回到 WBS 调整计划、通过事项推动行动、在风险登记册补充应对，并在需要时提交审批。此处形成“发现偏差—分析原因—采取措施—再次观察”的控制循环。

### 第八步：结项、归档与可追溯恢复

项目达到验收条件后，补齐交付文档，发起项目完成审批。项目资料、基线、事项、风险、审批和沟通记录共同构成项目档案；系统备份与事件日志保证后续审计、交接或恢复时仍可追溯。

## 7. 不同角色通常如何使用系统

| 角色 | 日常最关注的模块 | 主要动作 | 最终责任 |
| --- | --- | --- | --- |
| 系统管理员 | 账号、角色权限、审批流程、助手设置、系统数据 | 配置账号、权限、流程、备份与恢复策略 | 系统安全、规则和可用性 |
| 管理层/经营负责人 | 经营驾驶舱、项目绩效、审批中心 | 看项目组合、审关键节点、关注偏差 | 资源和关键决策 |
| 项目经理 | 项目信息、WBS、执行驾驶舱、事项、风险、预算、审批 | 建计划、分配责任、推动问题、申请决策、结项 | 项目目标达成与过程受控 |
| 阶段负责人/项目成员 | WBS、事项、风险、协同、文档 | 更新任务、处理事项、报告风险、上传交付物 | 自己负责工作的完成质量与时效 |
| 审批人 | 审批中心、协同、相关文档 | 审核材料、给出通过/退回/拒绝意见 | 对授权决定负责 |

实际可执行范围由组织配置的权限树和审批流程决定；上表描述的是典型职责分工，而非固定岗位限制。

## 8. 对外演示建议：用“闭环”而不是“菜单”来讲

如果面对首次接触系统的人，建议按下面顺序演示，而不是从菜单逐项点击：

1. **先展示项目档案**：项目是什么、服务谁、由谁负责。
2. **再展示 WBS**：怎样把目标拆成任务、负责人和时间。
3. **切换到执行驾驶舱**：怎样从一堆任务中抓住阶段状态和预警。
4. **点开事项和风险**：怎样把现场问题落实到责任人并关联计划影响。
5. **展示文档和预算**：怎样同时保留交付证据和经营边界。
6. **发起一次审批或 Gate**：说明关键动作为什么不能只靠口头确认。
7. **查看绩效**：说明系统怎样从“记录项目”升级到“帮助判断项目是否健康”。
8. **最后展示协同、日志与备份**：说明人员变动后，项目为什么仍可追溯、可交接。

这条讲解线能让听众自然理解：每个模块都不是独立卖点，而是项目闭环中的一个环节。

## 9. 系统当前能力边界说明

- WBS 排期已区分业务依赖与负责人资源约束：资源冲突不会被简单写成业务紧前关系。
- 个人临时不可用时间不作为项目计划中的正式资源日历记录；项目排期以项目工作日历和负责人容量为依据。
- MPP 二进制导出需要已配置的转换服务；导入/导出能力应结合部署环境确认。
- 文档上传、WebDAV、定时备份、智能助手本地服务等能力依赖相应的部署与配置。
- 系统数据清理是不可逆操作，应在确认备份有效、明确保留策略后由管理员执行。

## 10. 结论：什么叫“项目管理闭环”

在 Ceastar PMS 中，一个项目闭环至少包含以下六件事：

1. **目标可定义**：有项目档案、合同边界和责任人；
2. **工作可计划**：有 WBS、工期、依赖、资源和正式基线；
3. **执行可跟踪**：有阶段、事项、风险、预警和沟通；
4. **结果可证明**：有文档、交付物和 Gate 审批；
5. **经营可判断**：有预算、实际信息和挣值绩效；
6. **过程可追溯**：有权限、审批、日志、备份和恢复能力。

因此，系统的价值不只是记录项目状态，而是将“计划、执行、决策、证据和复盘”连接成一套能持续运行的项目管理机制。
